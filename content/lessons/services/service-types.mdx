A ClusterIP Service is reachable only from inside the cluster. To accept traffic from outside — a browser, another data centre, a load balancer in front of the cluster — you need a different **Service type**. The types are not alternatives so much as **layers**: each one adds something on top of the previous.

<Phase step="theory" />

## The layers

| Type | Adds | Reachable from | Typical use |
|---|---|---|---|
| `ClusterIP` | A virtual IP + DNS name | Inside the cluster | Service-to-service traffic (the default) |
| `NodePort` | A ClusterIP **plus** the same port (30000–32767) opened on **every node** | Anything that can reach a node IP | Bare-metal, labs, behind an external load balancer you manage |
| `LoadBalancer` | A NodePort **plus** an external load balancer provisioned by a controller | The load balancer's external IP | Cloud clusters; on-prem with MetalLB or similar |
| `ExternalName` | Only a DNS `CNAME` to an external name — no IP, no proxying | Inside the cluster | Giving an external database a cluster-local name |

Two more knobs change *how* a Service behaves rather than where it is reachable:

- **Headless Services** (`clusterIP: None`): no virtual IP at all. DNS returns the **Pod IPs** directly. StatefulSets depend on this so each replica gets a stable DNS name (`db-0.db.default.svc.cluster.local`).
- **Traffic policies**: `externalTrafficPolicy` and `internalTrafficPolicy` decide whether traffic may be forwarded to a backend on *another* node.

<Callout type="note" title="Who implements LoadBalancer?">
Kubernetes itself never creates a cloud load balancer. A **cloud controller manager** (on AWS, GCP, Azure…) or an add-on such as MetalLB watches for `type: LoadBalancer` Services and provisions one. Without such a controller the Service stays with `EXTERNAL-IP <pending>` forever — a frequent "bug" that is really a missing component.
</Callout>

## externalTrafficPolicy: Cluster vs Local

With the default **`Cluster`** policy, any node accepts NodePort traffic and may forward it to a Pod on another node. The extra hop requires **SNAT**, so the Pod sees the node's IP, not the client's.

With **`Local`**, a node only forwards to Pods running **on itself**. The client IP is preserved and there is no extra hop — but a node with no local Pod drops the traffic. Cloud load balancers handle that through a health check port (`healthCheckNodePort`) that only succeeds on nodes with local endpoints.

| | `Cluster` (default) | `Local` |
|---|---|---|
| Client source IP visible to Pod | No (SNAT) | Yes |
| Extra network hop possible | Yes | No |
| Uneven load across Pods | Even | Can be uneven (per node, not per Pod) |
| Node without a local Pod | Forwards | Drops |

## Creating NodePort and LoadBalancer Services

<Terminal
  command="kubectl -n svc-lab expose deployment web --name=web-np --type=NodePort --port=80 --target-port=80"
  output="service/web-np exposed"
/>

<Terminal
  command="kubectl -n svc-lab get service web-np"
  output={`NAME     TYPE       CLUSTER-IP      EXTERNAL-IP   PORT(S)        AGE
web-np   NodePort   10.96.211.47    <none>        80:31742/TCP   4s`}
/>

`80:31742/TCP` reads as **service port 80, node port 31742**. The node port was picked at random from the range. In YAML you can pin it, which exam tasks often require:

```yaml title="web-np.yaml"
apiVersion: v1
kind: Service
metadata:
  name: web-np
  namespace: svc-lab
spec:
  type: NodePort
  selector:
    app: web
  ports:
    - port: 80          # ClusterIP port, still works inside the cluster
      targetPort: 80    # container port
      nodePort: 30080   # must be inside --service-node-port-range (default 30000-32767)
```

To reach a NodePort, you need a **node IP**:

Note that **every** node answers on the node port, including the control plane node and nodes that run none of the Pods — kube-proxy forwards.

A LoadBalancer Service is created the same way with `--type=LoadBalancer`. On a plain kind cluster you will see:

<Terminal
  command={`kubectl -n svc-lab expose deployment web --name=web-lb --type=LoadBalancer --port=80
kubectl -n svc-lab get service web-lb`}
  output={`NAME     TYPE           CLUSTER-IP     EXTERNAL-IP   PORT(S)        AGE
web-lb   LoadBalancer   10.96.88.140   <pending>     80:30914/TCP   10s`}
/>

`<pending>` is expected: nothing in a bare kind cluster implements LoadBalancer. The `sigs.k8s.io/cloud-provider-kind` project, run on your host, provisions one for kind clusters; on-prem clusters typically use MetalLB. The node port (`30914`) works regardless, because a LoadBalancer Service is still a NodePort Service.

## ExternalName

```yaml title="db-external.yaml"
apiVersion: v1
kind: Service
metadata:
  name: orders-db
  namespace: svc-lab
spec:
  type: ExternalName
  externalName: orders.db.example.com   # a DNS name, never an IP
```

Pods can now use `orders-db.svc-lab` and CoreDNS answers with a `CNAME` to `orders.db.example.com`. Nothing is proxied, ports are not remapped, and TLS certificates must still match the external name — which is why ExternalName is less useful for HTTPS than it looks.

## Example: preserving the client IP

```yaml title="web-local.yaml"
apiVersion: v1
kind: Service
metadata:
  name: web-local
  namespace: svc-lab
spec:
  type: NodePort
  externalTrafficPolicy: Local    # keep the client IP; only nodes with a local Pod answer
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80
      nodePort: 30081
```

Scale `web` to **one** replica and call port `30081` on each node IP from a client Pod: only the node hosting the Pod answers; the others time out. With `Cluster`, all three answer. That difference is exactly what a cloud load balancer's health check uses to stop sending traffic to empty nodes.

## Independent challenge

<Exercise kind="challenge" title="Give an external service an in-cluster name">

Applications in namespace `shop` must reach a payment API at `api.payments.example.com` using the name `payments` (port 443), so that the address can later be swapped for an in-cluster Service without changing the applications.

Create what is needed and explain how to verify it from a Pod, given that the domain does not really exist.

<Solution>

```bash
kubectl create namespace shop
kubectl -n shop create service externalname payments --external-name=api.payments.example.com
kubectl run client -n shop --rm -it --restart=Never --image=busybox:1.36 -- nslookup payments
```

`nslookup` shows `payments.shop.svc.cluster.local canonical name = api.payments.example.com` followed by a resolution failure for the external name — which proves the Service is correct; only the (fictional) target does not resolve. Later, replacing it with a `ClusterIP` Service of the same name redirects every client without a configuration change.

</Solution>
</Exercise>

## Troubleshooting

<Exercise kind="troubleshooting" title="The node port that was refused">

A colleague applies a Service with `nodePort: 8080` and the API server rejects it. Another Service of type `LoadBalancer` has shown `<pending>` for an hour. Explain both before reading on.

<Solution>

The first is a validation error from the API server:

```text
The Service "web-np" is invalid: spec.ports[0].nodePort: Invalid value: 8080:
provided port is not in the valid range. The range of valid ports is 30000-32767
```

Node ports come from the API server's `--service-node-port-range` (default `30000-32767`). Either use a port inside the range, or omit `nodePort` and let Kubernetes allocate one.

The second is not an error at all: no controller in the cluster implements `LoadBalancer`. Check for a cloud controller manager or MetalLB (`kubectl get pods -A | grep -i -e metallb -e cloud-controller`). Until one exists, use the NodePort that the Service already has, or an Ingress/Gateway.

</Solution>
</Exercise>

<Callout type="mistakes">

- Expecting `type: LoadBalancer` to work on bare-metal or kind without an implementation.
- Choosing a `nodePort` outside the configured range.
- Using `externalTrafficPolicy: Local` with Pods on only some nodes and then wondering why some node IPs time out.
- Putting an **IP address** in `externalName`. It must be a DNS name.

</Callout>
