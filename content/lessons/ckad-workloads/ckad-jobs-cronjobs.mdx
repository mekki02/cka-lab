Not everything is a server. Migrations, imports, reports and backups start, do their work and **finish**. A Job runs Pods until a given number of them succeed, retrying the ones that fail; a CronJob creates Jobs on a schedule. Both appear in almost every CKAD exam, usually with one field you must find with `kubectl explain`.

<Phase step="theory" />

## How a Job works

A Job creates Pods from its template and counts **successful completions**. When enough Pods have exited with code 0, the Job is **Complete**. When too many fail, it is **Failed**.

| Field (`spec.`) | Default | Meaning |
|---|---|---|
| `completions` | 1 | How many successful Pods the Job needs |
| `parallelism` | 1 | How many Pods may run at the same time |
| `backoffLimit` | 6 | How many retries before the Job is Failed |
| `activeDeadlineSeconds` | none | Hard time limit for the whole Job, retries included |
| `ttlSecondsAfterFinished` | none | Delete the Job (and its Pods) this long after it finishes |
| `completionMode` | `NonIndexed` | `Indexed` gives each Pod a number in `JOB_COMPLETION_INDEX` |
| `template.spec.restartPolicy` | — | **Must** be `Never` or `OnFailure` |

`restartPolicy` decides **where** retries happen: with `OnFailure`, the kubelet restarts the container inside the same Pod; with `Never`, the Job controller creates a **new Pod** for each attempt — so you keep every failed Pod and its logs.

## How a CronJob works

A CronJob holds a **Job template** and a **schedule** in cron syntax. At each tick it creates a Job named `<cronjob>-<timestamp>`.

```text
┌───────── minute (0-59)
│ ┌─────── hour (0-23)
│ │ ┌───── day of the month (1-31)
│ │ │ ┌─── month (1-12)
│ │ │ │ ┌─ day of the week (0-6, Sunday = 0)
* * * * *
```

| Schedule | Runs |
|---|---|
| `*/5 * * * *` | every 5 minutes |
| `0 2 * * *` | every day at 02:00 |
| `30 8 * * 1-5` | at 08:30, Monday to Friday |
| `0 0 1 * *` | at midnight on the first of each month |

| Field (`spec.`) | Default | Meaning |
|---|---|---|
| `concurrencyPolicy` | `Allow` | `Forbid` skips a run while the previous one still runs; `Replace` stops it |
| `successfulJobsHistoryLimit` | 3 | Finished Jobs kept |
| `failedJobsHistoryLimit` | 1 | Failed Jobs kept |
| `startingDeadlineSeconds` | none | A run missed by more than this (controller down…) is skipped |
| `suspend` | false | Pause the schedule |
| `timeZone` | controller's | e.g. `Europe/Paris` |

## Jobs

```bash
k create job hello --image=busybox:1.36 -- sh -c 'echo hello; sleep 5'
k get jobs                            # COMPLETIONS 0/1 → 1/1
k get pods -l job-name=hello          # Job Pods are labelled job-name=<job>
k logs job/hello                      # logs of (one of) its Pods
k wait --for=condition=complete job/hello --timeout=60s
k delete job hello                    # also deletes its Pods
```

The generator cannot set `completions`, `parallelism` or `backoffLimit`: generate and edit.

```bash
k create job batch --image=busybox:1.36 $do -- sh -c 'echo working; sleep 3' > batch.yaml
```

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: batch
spec:
  completions: 6          # added
  parallelism: 3          # added
  backoffLimit: 2         # added
  template:
    spec:
      containers:
      - name: batch
        image: busybox:1.36
        command: ["sh", "-c", "echo working; sleep 3"]
      restartPolicy: Never
```

## CronJobs

```bash
k create cronjob report --image=busybox:1.36 --schedule='*/15 * * * *' -- sh -c 'date; echo report'
k get cronjob report                  # SCHEDULE, SUSPEND, ACTIVE, LAST SCHEDULE
k create job report-now --from=cronjob/report    # run it once, now — perfect for testing
k get jobs
k patch cronjob report -p '{"spec":{"suspend":true}}'
```

<Callout type="exam" title="Exam tip">
Never wait for a schedule to test a CronJob. `k create job <name> --from=cronjob/<cronjob>` creates a Job from its template immediately; check its logs, then delete it if the task did not ask for it.
</Callout>

## Practical example: a Job that fails properly

```bash
k create job flaky --image=busybox:1.36 $do -- sh -c 'echo trying; exit 1' > flaky.yaml
yq -i '.spec.backoffLimit = 2' flaky.yaml      # or edit with vim
k apply -f flaky.yaml
k get pods -l job-name=flaky -w                  # 3 Pods: the first try + 2 retries, all Error
k describe job flaky | grep -A3 Conditions       # Failed … BackoffLimitExceeded
```

Retries are spaced with an exponential back-off (10 s, 20 s, 40 s…), so failing Jobs take longer than you expect — use `activeDeadlineSeconds` when there is a time budget.

<Exercise kind="guided" title="Parallel batch">

1. Create the `batch` Job above (6 completions, 3 in parallel).
2. While it runs, count how many Pods run at the same time (`k get pods -l job-name=batch`).

<Solution>

```bash
k apply -f batch.yaml

k wait --for=condition=complete job/batch --timeout=120s
k get job batch -o jsonpath='{.status.succeeded}{"\n"}'     # 6
```

</Solution>

## Independent challenge

<Exercise kind="challenge" title="A careful nightly job">

Create a CronJob `backup` that runs `busybox:1.36` with `echo backup` at 01:30 every day, never runs two backups at the same time, keeps only the last successful and the last failed Job, and gives each run at most 2 minutes. Then prove it works without waiting until 01:30.

<Solution>

```bash
k create cronjob backup --image=busybox:1.36 --schedule='30 1 * * *' $do -- sh -c 'echo backup' > backup.yaml
```

```yaml
spec:
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 1
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      activeDeadlineSeconds: 120     # in the JOB spec, not the CronJob spec
      template: …
```

```bash
k apply -f backup.yaml
k create job backup-test --from=cronjob/backup
k logs job/backup-test        # backup
```

`activeDeadlineSeconds` belongs to the Job (`spec.jobTemplate.spec`); a CronJob's own `startingDeadlineSeconds` is something else — how late a missed run may still start.

</Solution>
</Exercise>

## Troubleshooting

<Exercise kind="troubleshooting" title="The Job that never finishes">

A Job `import` shows `COMPLETIONS 0/1` for ten minutes and its Pod `Running`. Another Job `export` was rejected with `spec.template.spec.restartPolicy: Unsupported value: "Always"`. Explain both.

<Solution>

`import`: the container's process never exits (a server, or `sleep infinity`), so the Pod never succeeds. A Job's command must terminate; add `activeDeadlineSeconds` to bound it. Check with `k logs job/import`.

`export`: Job Pods must use `restartPolicy: Never` or `OnFailure`. `Always` would restart a finished container forever. `kubectl create job` sets `Never` for you — this happens when a Pod or Deployment manifest is copied into a Job by hand.

</Solution>
</Exercise>

<Callout type="mistakes">

- Putting `completions`/`parallelism` under the CronJob's `spec` instead of `spec.jobTemplate.spec`.
- Unquoted schedules on the command line: the shell expands `*` into file names.
- Forgetting `-- sh -c '…'` for commands with `;`, pipes or variables.
- Setting `ttlSecondsAfterFinished` when the task wants the Job to be inspected later: it deletes the Job.

</Callout>

## Knowledge check

<KnowledgeCheck
  question="A Job has completions: 4, parallelism: 2 and restartPolicy: Never. One Pod fails once. How many Pods exist when the Job is Complete (no TTL)?"
  options={['4', '5', '2', '6']}
  answer={1}
  explanation="With restartPolicy Never, every failed attempt is a new Pod: 4 successful Pods plus 1 failed Pod = 5. With OnFailure, the container would be restarted inside the same Pod instead."
/>

<KnowledgeCheck
  question="A CronJob runs every minute, but each run takes three minutes. You want at most one run at a time, skipping runs that would overlap. Which setting?"
  options={['concurrencyPolicy: Replace', 'concurrencyPolicy: Forbid', 'parallelism: 1', 'suspend: true']}
  answer={1}
  explanation="Forbid skips a scheduled run while the previous Job is still active. Replace would cancel the running Job and start a new one; parallelism applies to Pods inside one Job."
/>
