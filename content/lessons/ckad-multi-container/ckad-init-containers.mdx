Sometimes an application cannot start until something else has happened: a file downloaded, a schema migrated, a dependency reachable. You could bake that logic into the image's entrypoint — or you can keep the app image clean and put the preparation in **init containers**: containers that run, one after the other, to completion, **before** the app containers start.

<Phase step="theory" />

## What containers in a Pod share

Before looking at init containers, remember what "same Pod" means:

| Shared | Not shared |
|---|---|
| Network: one IP, one port space — containers reach each other on `localhost` | Filesystem: each container has its own image's filesystem |
| Volumes: any volume declared in the Pod can be mounted by any container | Processes (unless `shareProcessNamespace: true`) |
| Lifecycle: scheduled together, on the same node, deleted together | Resources: requests/limits are per container |

So containers in a Pod exchange data through a **shared volume** (often an `emptyDir`) or over **localhost**.

## Init containers

`spec.initContainers` is a list of containers that:

1. run **in order**, each one only after the previous one **exited 0**;
2. must all succeed before any container in `spec.containers` starts;
3. are retried according to the Pod's `restartPolicy` when they fail (with `Always` or `OnFailure`, the failing init container is restarted; with `Never`, the Pod fails);
4. have no probes — they are supposed to finish.

They are ideal for:

- **preparing data**: render a config file, clone content, set permissions on a volume;
- **waiting for a dependency**: loop until a Service resolves or a port answers;
- **keeping secrets of the build out of the app**: a tool that only the init container needs.

## Status while initialising

| STATUS | Meaning |
|---|---|
| `Init:0/2` | None of the two init containers has completed yet |
| `Init:1/2` | The first finished, the second is running |
| `Init:Error` | An init container exited non-zero |
| `Init:CrashLoopBackOff` | An init container keeps failing and is being restarted |
| `PodInitializing` | All init containers done, app containers starting |

## Declaring init containers

There is no flag for them: generate the Pod and add the list.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web
spec:
  initContainers:
  - name: render
    image: busybox:1.36
    command: ["sh", "-c", "echo '<h1>built at '$(date)'</h1>' > /work/index.html"]
    volumeMounts:
    - name: site
      mountPath: /work
  containers:
  - name: web
    image: nginx:1.27
    volumeMounts:
    - name: site
      mountPath: /usr/share/nginx/html
  volumes:
  - name: site
    emptyDir: {}
```

The same volume is mounted at **different paths** in the two containers — what matters is the volume name.

## Inspecting them

```bash
k get pod web                              # Init:0/1 → PodInitializing → Running
k logs web -c render                       # logs of an init container: name it with -c
k describe pod web                         # "Init Containers:" section with state and exit code
k get pod web -o jsonpath='{.status.initContainerStatuses[0].state}'
```

## Waiting for a dependency

```yaml
initContainers:
- name: wait-for-db
  image: busybox:1.36
  command: ["sh", "-c", "until nslookup db.$(cat /var/run/secrets/kubernetes.io/serviceaccount/namespace).svc.cluster.local; do echo waiting for db; sleep 2; done"]
```

A shorter form usually works too: `until nslookup db; do sleep 2; done` — the Pod's DNS search path adds the namespace. The Pod stays in `Init:0/1` until a Service named `db` exists.

<Callout type="exam" title="Exam tip">
`kubectl logs <pod>` without `-c` picks the **app** container (or asks you to choose). For an init container that is stuck, always use `kubectl logs <pod> -c <init-container>`.
</Callout>

## Practical example: two steps, in order

```yaml
initContainers:
- name: step-1
  image: busybox:1.36
  command: ["sh", "-c", "echo one >> /work/log; sleep 3"]
  volumeMounts: [{ name: work, mountPath: /work }]
- name: step-2
  image: busybox:1.36
  command: ["sh", "-c", "echo two >> /work/log"]
  volumeMounts: [{ name: work, mountPath: /work }]
containers:
- name: app
  image: busybox:1.36
  command: ["sh", "-c", "cat /work/log; sleep 3600"]
  volumeMounts: [{ name: work, mountPath: /work }]
volumes:
- name: work
  emptyDir: {}
```

`k logs <pod> -c app` prints `one` then `two`: step 2 never starts before step 1 has exited.

## Guided exercise

<Exercise kind="guided" title="Serve a page built by an init container">

1. Apply the `web` Pod from above.
2. Watch it with `k get pod web -w` until it is Running.
3. Check the page from inside the nginx container: `k exec web -c web -- curl -s localhost`.

<Solution>

The page shows `built at <date>`. The init container wrote `index.html` into the `emptyDir`, which nginx then serves from `/usr/share/nginx/html`. Restart the Pod (`k delete pod web` and re-apply) and the date changes: the `emptyDir` is created fresh with each Pod.

</Solution>
</Exercise>

## Independent challenge

<Exercise kind="challenge" title="Do not start before the API exists">

Create a Pod `client` (image `busybox:1.36`, command `sleep 3600`) that only starts once a Service named `orders` exists in its namespace. Show that it waits, then create the Service and watch it start.

<Solution>

```yaml
spec:
  initContainers:
  - name: wait-for-orders
    image: busybox:1.36
    command: ["sh", "-c", "until nslookup orders; do echo waiting; sleep 2; done"]
  containers:
  - name: client
    image: busybox:1.36
    command: ["sleep", "3600"]
```

```bash
k apply -f client.yaml; k get pod client          # Init:0/1
k logs client -c wait-for-orders                   # waiting…
k create service clusterip orders --tcp=80:80
k get pod client -w                                # PodInitializing → Running
```

</Solution>
</Exercise>

## Troubleshooting

<Exercise kind="troubleshooting" title="Init:CrashLoopBackOff">

A Pod shows `Init:CrashLoopBackOff`. `k logs <pod>` prints `container "app" in pod is waiting to start: PodInitializing`. How do you find the real error?

<Solution>

The app container has not started, so it has no logs. Find the failing init container in `k describe pod <pod>` (section *Init Containers*, look for `Last State: Terminated` with a non-zero exit code), then read **its** logs: `k logs <pod> -c <init-name> --previous`.

</Solution>
</Exercise>

<Callout type="mistakes">

- Mounting the shared volume in the init container but not in the app container (or using different volume names).
- Init containers that never exit (`sleep infinity`): the app never starts.
- Forgetting `-c` when reading init container logs.
- Expecting init containers to run again when only an app container restarts — they run once per Pod start.

</Callout>
